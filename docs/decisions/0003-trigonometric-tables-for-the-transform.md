# ADR-0003：变换所需三角常量的来源

- 状态：Accepted
- 日期：2026-08-13
- 关系：补充 [ADR-0002](0002-numeric-format-for-reconstruction.md) 第 3 条，并推翻其中「依赖 `libm`」一节关于**构建期**的结论（运行期的否决保留）

## 背景

ADR-0002 第 3 条要求「一切超越函数由查表或位构造给出」，并对 `|q|^(4/3)` 给出了完全整数的正确舍入判据：`v = m × 2^e` 是 `q^(4/3)` 的最近 f32，当且仅当 `v³` 与 `q⁴` 的整数比较落在相应中点的同侧。这条路走得通，靠的是 `v³ = q⁴` 这个代数出口。

`5.5` 的三角函数与零阶修正贝塞尔函数**没有对应的出口**——它们的值是超越数，任何有限整数关系都只是逼近。ADR-0002 因此在此无法直接执行（规范可追踪性 §5.18）。

需要的常量有三类：

| 用途 | 函数 | 出处 |
|---|---|---|
| 前/后旋转因子 | `xcos1[k] = −cos(2π(8k+1)/16N)`、`xsin1[k] = −sin(…)`，`k = 0…N/2−1` | `Pseudocode 60`、`62` |
| IFFT 旋转 | `cos(4πkn/N)`、`sin(4πkn/N)` | `Pseudocode 61` |
| KBD 窗 | `I(x) = Σ (x^k / (2^k k!))²`，再前缀求和、归一、开方 | `5.5.3` |

### 三类的难度并不相同

把它们拆开看，只有三角函数真正缺实现：

- **`I(x)` 不是超越函数依赖**，而是一个全正项级数。按 `term_k = term_{k−1} × (x/2) / k`、`sum += term_k²` 迭代，α = 6（`x` 最大 `6π ≈ 18.85`）时在 `k = 33` 停止，含 `term_0` 共 34 项。四则运算即可，IEEE 754 已完全定义其结果。
- **平方根在 IEEE 754 中是正确舍入的运算**，与 `+ − × ÷` 同级，因此任何合规实现给出的位模式必然相同。实测印证 `libm` 合规：f32 正规格化全域等步长抽样 2 086 882 个值、f64 随机抽样 2 998 556 个值，`libm` 与硬件指令位模式**零差异**。
- **`cos`/`sin` 没有这种保证**，IEEE 754 未强制它们正确舍入，各家实现可以不同。

## 决策

1. **已引入 `libm` 作为唯一构建期依赖，固定版本，关闭默认 feature。**

   ```toml
   [build-dependencies]
   libm = { version = "=0.2.16", default-features = false }
   ```

   `libm` 是 rust-lang 维护的 musl libm 纯 Rust 移植（`rust-lang/compiler-builtins`，MIT，MSRV 1.63），无传递依赖，自身构建脚本只做 cfg 探测。版本由 `=` 精确锁定并由版本控制中的 `Cargo.lock` 二次固定——CI 全程 `cargo --locked`，锁文件与清单不一致时构建即失败。目标侧依赖仍为零。

   关闭默认的 `arch` feature 不改变任何表值（两种配置下摘要相同，已实测），并排除可选的架构优化路径。它不等于源码中不存在目标条件分支；确定性契约最终由下述冻结摘要闭锁，而不是依赖「绝无平台分支」这一假设。

   `arch` 之外仍有必要的 `target_arch` 条件。与 `cos`/`sin` 相关的路径中，`rem_pio2` 会在 x86 无 SSE2 时用 `force_eval!` 把 x87 的 80 位中间结果强制舍回 f64，以抑制超精度差异；若其他目标条件仍造成输出漂移，第 3 条的摘要会让该平台构建失败，而不会静默产出另一张表。

2. **目标侧不链接 `libm`，运行期不调用任何超越函数。** 它只出现在 `[build-dependencies]`，`no_std` 目标的依赖图不受影响。运行期只有查表与四则运算。

3. **每张生产表的完整位序列都必须冻结 SHA-256，构建期重算比对，不符即中止构建。** 布局必须逐字节固定，否则摘要无意义：

   | 表 | 布局 | 规模 | SHA-256 |
   |---|---|---|---|
   | `IMDCT_ROTATION` | 按 `TRANSFORM_LENGTHS_48` 顺序，每个 `N` 取 `k = 0…N/2−1`，依次写 `xcos1[k]`、`xsin1[k]` | 10 664 个 f32 = 42 656 字节 | `cd702daceaf47a407381e8238ab43c310e3f4c8139a17d84b66ccd4481da524e` |
   | `KBD_LEFT` | 同一长度顺序，每个 `N_W` 取 `n = 0…N_W−1`，写 `KBD_LEFT(N_W, n)` | 10 664 个 f32 = 42 656 字节 | `6e57e7e89e52b5b57b27ab81b5472aeabacb1a88d00ddb76fdc313835fc0c895` |
   | `IFFT_ROOTS` | 同一长度顺序，令 `M=N/2`，每个 `M` 取 `e=0…M−1`，依次写 `cos(2πe/M)`、`sin(2πe/M)` | 10 664 个 f32 = 42 656 字节 | `76261b2212836ee22fbf162ea6a2bcc35233bdd54dec8fa60cb15b51a452ef6b` |
   | `QMF_MODULATION` | `k = 0…511`，依次写 `cos(2πk/512)`、`sin(2πk/512)` | 512 个复数 = 4 096 字节 | `4e7f81b7353b5e1915d249615dbd2746ac7db1cb830f9d6abb2f6c451d820d25` |

   每项取 `f32::to_bits().to_le_bytes()` 顺序连接后计算摘要。前三张表的布局都覆盖十五档变换长度的全域，不按实测材料缩表——理由与反量化表相同：解码器必须能处理规范允许的任何长度。

   第四张是 `5.7.3`/`5.7.4` 的 QMF 调制相位。两条伪码的指数都是 `j·(π/128)·(sb+0.5)·m`（分析 `m = 2n−1`，合成 `m = 2n−255`），化简为 `2π·(2sb+1)·m / 512`，故查一张 512 点的整圈表即可。`(2sb+1)·m` 恒为奇数，实际只用得到 256 个奇数下标；仍按整圈存是因为省下的 2 KiB 不值得多一层容易写反的奇偶换算。生成规则与 `IFFT_ROOTS` 相同：只在第一象限调用 `libm`，轴点精确写入，其余三象限由对称与共轭派生。

   `5.7.3` 表 D.3 的 QMF 原型窗 `QWIN[640]` **不在本 ADR 的范围内**：它不是算出来的，而是逐字取自规范随附 C 表的 `const float QWIN[640]`，与 Huffman 码本同源。`build.rs` 仍冻结了它的摘要，但那只保证「解析与 f32 化没有走样」；真正说明这 640 个数是一张能重建的原型窗的，是两条与摘要无关的结构判据——镜像仅在 128 的倍数处反号，以及每个多相相位的 `Σ_k QWIN[64k+p]² = 1`（实测最大偏差 `2.8×10⁻⁷`）。

4. **KBD 右窗不单独建表。** `KBD_RIGHT(N, 2N−1−n) = KBD_LEFT(N, n)`：右窗求和上限为 `2N−n−1`，代入即得左窗的求和上限 `n`。实现按逆序索引读同一张表。

5. **`I(x)` 与 KBD 的求和过程逐条固定，因为它们决定表的位。** 摘要只在算法完全确定时才是可复现的：

   - `I(x)`：`term_0 = 1`，`term_k = term_{k−1} × (x/2) / k`，`sum` 从 `1` 起按 `k` 升序累加 `term_k²`；终止条件 `term_k² ≤ sum × f64::EPSILON / 4`。
   - `W(N, p, α) = I(πα √(1 − (2p/N − 1)²)) / I(πα)`，`p = 0…N`（含端点，共 `N+1` 项）；`α` 按表 186 用 `N_W` 查得，不是用块长 `N`。
   - `KBD_LEFT(N, n) = √(S(n) / S(N))`，`S` 为 `W` 按 `p` 升序的前缀和。
   - 全程 f64（开方用 `libm::sqrt` 而非 `sqrtf`，少一次中间舍入），只在写表时统一收窄为 f32。

6. **初始表值由高精度审计锚定，构建期另做结构自洽检查。**

   - 离线审计以 100 位十进制精度（约 332 bit）全域复算三角函数与 KBD，载体是 `scripts/check_transform_tables.py`；π 由 Machin 公式算出，`cos`/`sin` 用泰勒级数，因此三角路径与生成侧独立。完整圆周的 IFFT 根与 QMF 调制表先在第一象限求值，再以换位、变号和共轭派生。KBD 按第 5 条的同一规范级数重算，但使用 Decimal 高精度与不同终止判据。每项按最近偶数直接收窄为 f32 后，四张表分别得到第 3 条记录的相同摘要；全部 33 016 项中舍入余数距 f32 中点最近的一项仍有 `7.11×10⁻⁵`，判定不在精度边缘。脚本直接读取本 ADR 的摘要，并按常量名递归读取 `build.rs` 与 `build_support/` 的四份生产摘要逐项交叉核对，文档、审计与实际构建不能静默漂移；任何摘要更新都必须通过该审计。脚本只用 Python 标准库，不进入正常构建依赖，并由 CI `quality` 检查运行。
   - 构建期把已存储的 f32 提升到 f64，再按每个 `N` 检查旋转因子：`abs(xcos1[k]² + xsin1[k]² − 1) ≤ 1×10⁻⁷`，两值均为负，且 `xcos1` 严格递增、`xsin1` 严格递减。单位圆实测最大偏差 `8.15×10⁻⁸`。
   - KBD 窗按每个 `N` 检查：`abs(KBD_LEFT(N,n)² + KBD_LEFT(N,N−1−n)² − 1) ≤ 1×10⁻⁷`，所有值位于 `(0, 1]` 且单调不减。Princen-Bradley 实测最大偏差 `8.04×10⁻⁸`。
   - IFFT 根按每个 `M` 检查：四个轴点逐位等于 `±1/+0.0`，共轭关系逐位成立，第一象限符号正确，且单位圆偏差不超过 `1×10⁻⁷`；实测最大偏差 `7.47×10⁻⁸`。

   两条平方恒等式只能证明内部配对自洽：共同角度偏移、成对符号翻转或成对重排仍可能保持平方和，因此不能充当正确性锚点；象限与顺序检查补足表结构，高精度摘要复算才锚定具体值。

7. **IFFT 算法、根表与生产内核已按 [ADR-0004](0004-mixed-radix-stockham-ifft.md) 落地。** 标量基线采用 radix-4/2/3/5 Stockham autosort；完整根表按第 3 条的 `IFFT_ROOTS` 布局生成，避免把常量集合绑定到蝶形专化。生成与审计都只在第一象限求值，再用换位/变号和共轭关系派生其余项；四个轴点精确写成 `±1` 与规范化的 `+0.0`，不能对有限精度的 π 调用三角函数来近似数学上的零。

8. **前/后旋转与 KBD 的生产表已按同一机制落地。** 两张表都按第 3 条的布局生成、核对冻结摘要，并在构建期跑第 6 条的结构判据；运行期只由 `asf::imdct` 按变换长度切片查表，不做任何三角求值。KBD 右窗按第 4 条逆序索引左窗，不单独建表。至此三张变换常量表齐备，`5.5` 余下的是展开、加窗与重叠相加的状态机。

## 理由

- **`std` 的 `cos` 不是 `libm` 的替代品，尽管它不需要任何依赖。** `build.rs` 本就链接 `std`，技术上可以直接调用。但 `std` 的实现来自平台 libm，跨平台会变：在本机的 10 664 个三角值上，`libm` 与 macOS `std` 的 f64 结果有 **365 个位模式不同**。用 `std` 生成，表值就由构建机决定。
- **f64 到 f32 的 29 位余量在本表中吸收了宿主差异。** 同样这 10 664 个值，收窄为 f32 后 `libm` 与 `std` 的差异为 **0 个**。`libm` 的 `cos` 精度约 1 ulp of f64 而非正确舍入，加上收窄时的双重舍入，理论上仍可能在真值极贴近 f32 中点时改变结果；第 6 条的高精度全域复算确认本表没有发生这种变化。
- **摘要保证的是「同一张表」，高精度复算才锚定「正确的表」。** 摘要不能独自发现所有机器一致地产生的错误；它只允许匹配冻结位序列的构建成功。正规格化 f32 相邻数的相对间距约在 `2⁻²⁴` 到 `2⁻²³` 之间，最大约 `1.19×10⁻⁷`；`2⁻²⁴ ≈ 6.0×10⁻⁸` 是最近舍入的半 ulp 误差界，并非 1 ulp。与参考解码器的端到端比对仍按 ADR-0002 使用容差，但该容差不代替表值审计。
- **版本锁定、冻结摘要、高精度锚点与结构检查各自承担一层责任。** `libm` 的纯 Rust 算法避开宿主平台 libm，目标条件分支仍由摘要闭锁；高精度审计确认冻结值及 f32 舍入，单位圆、象限、顺序与 Princen-Bradley 条件则在每次构建中防止布局或生成逻辑损坏。所有成功构建因而得到同一张已审计的表。
- **代价与收益不成比例的路径被排除。** 见下。

## 影响

正面影响：

- IFFT 根表与标量内核已进入默认 `no_std` 构建，完整 IMDCT 可在其上继续接前/后旋转与窗口。
- 表值唯一确定；所有成功的跨机器构建产出相同的 `.rodata`，回归基线仍可按位冻结。
- `I(x)` 的自实现是几十行全正项级数，可逐项审计；它同时是 KBD 表唯一的非平凡计算。

代价：

- 工作区现为**目标侧零依赖，构建期只依赖精确锁定的 `libm`**。
- 首次构建需要网络或已填充的 registry 缓存。若离线构建成为需求，应 vendor `libm` 而非放宽版本约束。
- 当前 IFFT 根表增加约 41.7 KiB `.rodata`；三张变换表全部落地后约 125 KiB，加 32 KiB 反量化表合计约 157 KiB。
- 升级 `libm` 版本时摘要可能变化。这是设计意图：变化将中止构建，须重复高精度审计并核对结构判据后再更新摘要，而不是随依赖升级悄悄漂移。

## 被否决方案

### 构建期大整数定点（ADR-0002 原路线的延伸）

在 `build.rs` 里用带严格误差界的区间算法算 `cos`/`sin`/`I₀`，逐步提高精度直到区间两端舍入为同一 f32。这是唯一能宣称「正确舍入」的路径，且不引入依赖。

否决的是把这套高精度区间算法维护在每次构建的生产路径中，而不是高精度核验本身。第 6 条已用 100 位十进制审计脚本离线复算全部 f32 位并固定摘要；正常构建只需用摘要闭锁结果并运行轻量结构检查，无须在 `build.rs` 中长期维护几百行定点代码和误差传播证明。

### 用 `std::f64::cos` 生成

零依赖，`build.rs` 已链接 `std`。但表值将由构建机的平台 libm 决定——实测 365/10 664 的 f64 差异说明这不是理论担忧。摘要冻结会把差异变成构建失败，于是在某些平台上根本无法构建。

### 依赖 `libm` 用于运行期

一行依赖即可让 `no_std` 目标直接调用 `cos`/`sin`。否决：运行期依赖会进入目标二进制并参与每次解码，而查表方案的运行期成本更低、结果更可复现。构建期与运行期的取舍不同，本 ADR 只放开前者。

### 表值直接写入版本控制

免去构建期工作与依赖。但四张表共 33 016 个 f32 字面量既不可读也无法逐项审计，且失去了「重算并比对」这一层保护——一旦有人手工改动某一项，没有任何机制会发现。

## 对 ADR-0002 的修订

ADR-0002 的以下表述被本 ADR 取代：

- 第 3 条标题「不引入 `libm`，不依赖 `std`」——限定为**运行期**；构建期允许锁定版本的 `libm`。
- 「不引入任何外部依赖」——改为目标侧零依赖。
- 被否决方案「依赖 `libm`」一节称「`libm` 的结果不保证跨版本位一致」。跨版本确实可能变（故本 ADR 精确锁版本）；纯 Rust 实现也确实避开宿主平台 libm，但仍存在必要的目标条件分支。本 ADR 不把跨平台契约建立在绝对同值假设上，而由冻结摘要保证所有成功构建接受同一位序列、差异平台闭锁失败。

`|q|^(4/3)` 的整数生成保持不变——它有代数出口，没有理由退回到浮点。
