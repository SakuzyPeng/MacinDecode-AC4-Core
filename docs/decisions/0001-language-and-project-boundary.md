# ADR-0001：语言与项目边界

- 状态：Accepted
- 日期：2026-07-24

## 背景

项目需要解析不可信的复杂变长码流，维护大量跨帧状态，执行高吞吐 DSP，并向 Swift、C++ 和其他宿主提供稳定接口。同时，现有对象型 AC-4 生产链位于一个独立的外部编码项目，其中包含平台相关的本地工具依赖。

## 决策

1. 解码核心使用 Rust 2024 edition。
2. 项目建立为独立 workspace，名称为 `MacinDecode-AC4-Core`。
3. DAMF 测试向量生成初期使用 Python，产物由官方 ADM 规范化工具处理。
4. macOS GUI 若需要，继续使用 Swift，但不承载解码算法。
5. 对外集成通过版本化 C ABI。
6. 外部编码项目是开发期测试向量生产者，不是运行时依赖；其名称、路径与内部实现不写入本仓库的公开文档，只通过未纳入版本控制的 `.env.local` 配置。
7. 标量 Rust 是正确性基线；性能优化只能替换局部、可差分验证的内核。
8. 不依赖 nightly-only portable SIMD。必要时在隔离模块中使用稳定平台 intrinsic 或外部内核。

## 理由

- Rust 适合表达带边界检查的 bit reader、枚举语法和显式状态所有权。
- 解析层的内存安全风险高于使用 C/C++ 可获得的早期便利。
- 现有 Rust 工具链已经具备 `staticlib`、`cbindgen` 和 Swift FFI 经验。
- 解码器独立后可以跨平台构建，也不会把宿主应用或厂商工具路径带入产品。
- Python 更适合快速生成文本 DAMF、确定性 PCM 和案例矩阵，但不进入运行时。

## 影响

正面影响：

- 解析器和状态机默认获得更强的内存安全保证。
- 与现有 Rust 工程和测试基础一致。
- 可以提供 C ABI，而不把公共接口绑定到 Rust 结构布局。
- 测试向量生产链与被测解码器保持代码独立。

代价：

- 规范中的 C 风格伪代码和 tables 需要可审计地转换为 Rust。
- SIMD 需要单独维护 ARM64/x86-64 路径，或等待标量性能数据后再决定。
- 若未来获得 C/C++ 参考实现，需要通过 FFI 构建差分测试后端。

## 被否决方案

### 全部使用 C++

便于移植传统 DSP 代码，但把复杂比特流解析和状态生命周期暴露给更多未定义行为及内存错误风险。仅当获得必须直接集成的参考源码时，才考虑把它作为隔离后端。

### 全部使用 Swift

便于 macOS UI，但不适合跨平台解码核心和底层 DSP/FFI 生态。

### 全部使用 Python

适合测试生成，不适合实时解码、稳定 ABI 和低层数值控制。

### 直接并入现有编码项目

会混合编码测试工具、专有本地 runtime 发现、容器处理与产品解码核心，增加平台耦合并削弱测试独立性。
