# 测试向量策略

## 1. 目标

本项目不把随机收集的节目流当作主要正确性依据。核心测试集由可重复构造的对象母版生成，使每个输入信号、对象位置、元数据更新时间和编码参数都有明确来源。

测试体系需要回答四个不同问题：

1. 码流结构是否解析正确。
2. OAMD 和状态时间线是否还原正确。
3. 音频及对象重建是否在可接受的数值范围内。
4. 整个渲染前场景是否能产生合理且稳定的下游结果。

## 2. 向量生产链

```text
Vector Case Manifest
    -> DAMF manifest + metadata + CAF PCM
    -> ADM 规范化工具
    -> ADM BWF
    -> 默认 AC-4 编码工具 / DME A-JOC CLI
    -> AC-4（DME 另保留 Level 与 timing manifest）
    -> dac4 / TOC inspection
    -> MacinDecode-AC4-Core regression
```

职责划分：

- 自有生成器负责确定性音频、对象定义和动态事件。
- ADM 规范化工具作为 DAMF 到 ADM BWF 的规范化与接受性边界。
- 默认 AC-4 编码工具负责既有对象型 AC-4；DME CLI 提供独立的 L3/L4 A-JOC 回归来源。
- MacinDecode-AC4-Core 的解码核心不调用编码工具，只消费已冻结的测试产物；向量生产由 `scripts/build_vector.sh` 驱动，工具路径全部取自未纳入版本控制的 `.env.local`。

CLI 的 `export-adm-bwf` 另提供一条 OAMD → ADM BWF 的直接试听与互操作验证路径。
标准配置强制写入 `BW64`/`ds64` 且不生成私有 `dbmd`；Logic 配置仍强制使用
64 位 `RF64`/`ds64`，并按公开 DBMD 段结构生成 Atmos metadata 与 supplemental metadata。
该兼容层只服务试听与 GUI/编码器互操作，不替换既有 DAMF 向量生产边界。

### 2.1 工具路径配置

生产链依赖的外部工具全部按本机路径解析，仓库内不保存其二进制、不写死路径、不描述其内部实现。路径由未纳入版本控制的 `.env.local` 提供，模板见 `.env.local.example`：

```bash
cp .env.local.example .env.local   # 按本机情况填写
./scripts/check_tools.sh           # 校验齐备性
./scripts/check_tools.sh --json    # 输出 provenance.json 的 tools 片段
```

变量含义见模板注释。外部工具视为不透明的黑盒：本项目只约定输入、输出和版本指纹，不依赖也不记录其实现方式。

不拷贝二进制的理由是可复现性而非仓库体积。外部工具可能有自身的本地运行时依赖，复制出的副本未必能在另一台机器上工作；副本同时会切断与源仓库 commit 及构建时间的关联，使 `provenance.json` 无法说明某个向量究竟由哪一版工具产生。`check_tools.sh` 因此在校验存在性之外记录 SHA-256 与 commit，并在可执行文件早于源仓库 HEAD 时告警。

### 2.2 输出目录

所有输出写入独立目录，不得把规范化工具的输出路径设为源 DAMF 所在路径。向量根目录由 `VECTORS_DIR` 指定，留空时使用仓库内 `./vectors`。

## 3. 测试案例描述

每个案例应由一个自有、可版本控制的描述文件生成。建议字段如下：

```json
{
  "case_id": "object_static_front_left",
  "sample_rate": 48000,
  "duration_samples": 96000,
  "frame_rate": "24",
  "offset_seconds": 3600,
  "bed": {
    "layout": "7.1.2",
    "signals": "silence"
  },
  "objects": [
    {
      "source_id": 10,
      "name": "probe-object-10",
      "signal": {
        "kind": "prbs",
        "seed": 10,
        "level_dbfs": -24.0
      },
      "events": [
        {
          "sample_pos": 0,
          "position": [-0.75, 0.75, 0.0],
          "ramp_length": 0,
          "gain_db": 0.0,
          "size": 0.0
        }
      ]
    }
  ],

```

案例描述是测试意图的唯一来源。生成后的 DAMF、ADM BWF 或 AC-4 不允许手工修改后继续使用同一 `case_id`。

## 4. 产物目录

```text
vectors/<case_id>/
  case.json
  source/
    master.atmos
    master.atmos.metadata
    master.atmos.audio
  normalized/
    master.wav
  encoded/
    master_ac4_256K.m4a
    master_ac4_448K.m4a
    master_ac4_768K.m4a
    master_ac4_dme_l3_768K.m4a
    master_ac4_dme_l4_768K_3dof.m4a
    master_ac4_dme_l4_1500K.m4a
    master_ac4_ims_256K.m4a
    master_ac4_ims_legacy_256K.m4a
  inspection/
    adm.json
    ac4_256K.json
    ac4_448K.json
    ac4_768K.json
  hashes.sha256
  provenance.json
```

大型 PCM、ADM BWF 和 AC-4 文件是否进入 Git 需另行决定。无论采用 Git LFS、外部制品库或本地缓存，`case.json`、inspection 和 hash 必须能够版本控制。

`provenance.json` 至少记录：

- 生成器版本和提交 ID。
- ADM 规范化工具的 SHA-256。
- AC-4 编码工具的 SHA-256 与源仓库提交 ID。
- DME A-JOC 编码器及其配套 MP4 muxer 的 SHA-256。
- DEE IMS 作业使用的包装器、engine binary 与 XML 模板 SHA-256。
- 编码档位、码率和所有可控参数。
- 每个输入与输出文件的 SHA-256。
- 操作系统和架构，仅用于定位工具链差异。

两份清单由 `scripts/record_provenance.py` 生成，工具指纹取自 `check_tools.sh --json`。
产物目录或作业声明的编码输出缺失时，脚本报错而非跳过：不完整的溯源比没有溯源更危险。

`build_vector.sh` 保留既有 `encodes` 数组的 ADM BWF 编码路径，并接受可选 `dme_ac4` 与
`dee_ims` 作业。`--profile` 默认为 `default`，因此旧命令与未配置可选工具的环境不改变行为；
`dme_ac4` 或 `dee_ims` 只跑对应后端，`all` 运行三条链。DME 作业严格区分 Level 3/4：

```json
"dme_ac4": [
  {"level": 3, "bitrate": 768},
  {"level": 4, "bitrate": 1500},
  {"level": 4, "bitrate": 768, "mode": "3dof"}
]
```

`mode` 缺省为 `general`。Level 3 只接受 320/448/768 kbit/s，Level 4 只接受
128/256/448/768/1500 kbit/s；`3dof` 仅允许 Level 4。普通作业读取规范化 ADM BWF；3DoF 作业
则把 canonical DAMF 复制到隔离 staging，仅把 manifest 提升为 `version: 0.6.0`、
`type: 3dof`，并直接交给 DME。canonical DAMF 保持 0.5.1/home，其他生产链不受影响。

DME 输出 raw AC-4 与 timing manifest；脚本验证唯一输出、完整采样时长和 raw 路径，再把
`offset`/`duration` 传给同版本官方 muxer。模式进入输出名，因此普通与 3DoF 作业可以使用
相同 Level/码率。临时输出通过校验后才原子替换目标，失败会保留既有向量。该后端只声明
A-JOC 能力，不把 3DoF 或纯对象 ADM 误标为 direct-object。

#### DME 3DoF 实测结论

以下结论来自 DME 4.0 / DEE 6.5.4 与仓库单对象 7.1.2 探针；它们描述已观察到的工具行为，
不扩大为所有编码器的规范要求：

- CLI 公开帮助只列 `general|music`，但 `--encoder mode=3dof` 可用；编码器会拒绝 Level 3、
  非 3DoF 输入，以及未启用该模式的 3DoF 输入。
- DAMF 0.5.1 的 `type: 3dof` 被拒绝；0.6.0 可由 `atmos_info --validate 1` 识别为
  `Atmos content type: 3dof`，并成功编码 288 000 samples / 143 帧的 L4 768K AC-4。
- 相同 PCM、轨迹和 `headTrackMode` 下，home/general 与 3dof/3dof 的 raw AC-4 逐字节一致
  （SHA-256 `f0ccf04e207cee31a3189583522707e5fe74bf4322aba806faa36e537f9fb347`）。
  当前样本的 A-JOC 拓扑同为 9.1 core、21 个对象、
  20 个动态对象；因此 presentation 类型与编码模式首先是输入门禁和预处理选择，不能单独
  当作码流中存在专用 3DoF 标志的证据。
- `headTrackMode` 才表达对象的具体跟踪策略。DAMF event 可为各对象写 `scene relative` 或
  `head relative`；AC-4 OAMD 可在统一设置时使用全局 disable，在混合设置时使用逐对象
  `b_head_track_disable_obj`。把探针的所有 event 从 scene-relative 改为 head-relative 后，raw
  AC-4 长度仍为 586 586 字节，SHA-256 从上述 `f0cc…` 变为
  `e3ec6e5306f72f5c696ff22fd28d2c991d394361fe5f0219db12e919f0d62529`；143 帧中只有
  60 个字节位置变化，拓扑统计不变，符合 OAMD 控制位及帧校验随之变化的预期。本生成器通过
  `static_fields.headTrackMode` 固定每个对象的值。
- 只把标签改成 3DoF 虽能通过工具验证，却不足以形成有诊断力的向量。正式案例还必须明确
  哪些对象留在场景坐标系、哪些对象跟随听者，并设计能区分旋转补偿的轨迹。3DoF 在这里指
  头部旋转跟踪，不包含听者平移；它也不等于 direct-object 编码。

DEE IMS 直接读取生成的 DAMF，只支持
64/72/112/144/256/320 kbit/s；每个作业可选择 `ims`/`ims_music` 和 legacy presentation：

```json
"dee_ims": [
  {"bitrate": 256, "encoding_profile": "ims", "legacy_presentation": false},
  {"bitrate": 256, "encoding_profile": "ims", "legacy_presentation": true}
]
```

DEE 包装器只访问 `DEE_WORKSPACE_ROOT` 映射的 Windows drive。脚本把 DAMF 与渲染后的官方
XML 复制到 `tmp_macinac4_ims.*` 隔离目录，编码 raw AC-4，经 GPAC `MP4Box -add ... -new`
原子提交为 M4A，
退出时清理 staging。模板必须使用 raw AC-4 output；未知字段、不支持的码率、重复输出名和越界
工作区路径全部失败关闭。本机路径只写入 `.env.local`。

`build_vector.sh` 要求所有最终产物恰含一条音频轨。编码器附带预览视频时，脚本用 MP4Box 只
移除视频轨，不重编码 AC-4；即使产物已存在也会执行这项校验。因此 `payload_sha256` 不会混入
与音频回归无关的视频负载。

**外部生产工具在 `provenance.json` 中只留指纹，不留路径与版本字符串。** 路径会暴露本机
布局；生产工具的 `sha256`、源仓库 `commit`，DME encoder/muxer 双重哈希，以及 DEE
包装器/engine/template 三重哈希已足以
判定是否为同一个工具组合。公开的诊断或重封装工具可另记版本字符串。如何取得工具属于
`.env.local` 与工具自身文档的范畴。`check_tools.sh` 的人类可读输出仍显示路径，它只在本机
终端出现，不进入版本控制。

### 4.1 可重复性与回归基准

同一 `case.json` 重跑整条链路，逐层比对结果如下：

| 层 | 产物 | 结果 |
|---|---|---|
| 生成器 | DAMF 三件套 | 逐字节一致 |
| 规范化 | ADM BWF | 逐字节一致 |
| 编码 | AC-4 `.m4a` | 仅 12 字节不同 |

那 12 个字节全部位于 `mvhd`、`tkhd`、`mdhd` 三个容器 box，各 4 字节，即封装时写入的创建与修改时间；**媒体负载 `mdat` 逐字节一致**，占文件 99.88%。

因此编码链在给定工具版本下是确定的，但**完整文件哈希不能用作回归基准**——它每次封装都会变化。`provenance.json` 为 MP4 产物额外记录 `payload_sha256`，即 `mdat` 内容的哈希，回归比较应以该值为准。`hashes.sha256` 保持标准格式与完整文件哈希，用途是校验本地副本完整性，两者职责不同。

判定非确定性时必须先排除这类容器字段差异，否则会把稳定的编码链误判为不可复现。

## 5. 诊断信号

普通音乐适合主观回归，不适合定位对象映射。基础测试优先使用：

- 单采样或短脉冲：检测时延、priming 和边界。
- 不同频率的整周期正弦：快速识别声道和基本增益。
- 扫频：观察带宽、频谱工具和失真。
- 固定种子的 PRBS/MLS：测量相关性、时延和串扰。
- 独立种子的低相关噪声：同时激活多个对象。
- 静音与近静音：检查状态更新是否错误依赖音频能量。

信号必须留出编码余量，默认峰值不高于 -12 dBFS；专门的满幅与异常案例除外。

## 6. 最小案例矩阵

### 6.1 结构与时间

- 不同 frame rate：**本编码链不可达**。源母版帧率不影响 AC-4，四种帧率产出的 `mdat` 逐字节相同，`frame_rate_index` 恒为 13（见 9.2e）。`frame_rate_multiply_info()`、`frame_rate_fractions_info()` 的非空分支与 `frame_rate_factor > 1` 时 `b_audio_ndot` 的重复读取，只能靠构造码流覆盖。
- 不同 frame sample count 和边界组合。
- 首帧、随机访问帧、连续帧和配置变化。
- MP4 priming、负 PTS、edit list 和 skip samples。
- 截断 access unit、损坏长度和非法索引。

### 6.2 Bed

- bed-only 静音和逐声道激活。
- bed 与对象同时存在。
- LFE 独立脉冲。
- 支持范围内的不同 bed 配置。

### 6.3 对象元数据

- 单个静态对象位于中心、左右、前后、上下和边界位置。
- 同一对象的阶跃位置变化。
- 带 `rampLength` 的连续运动。
- 一帧内零次、一次和多次更新。
- gain、size、active、importance 和可用扩展字段变化。
- 多对象重合、交叉和分离。
- reset 后首帧状态恢复。

### 6.4 对象音频

- 单对象独占信号。
- 多对象使用不同 PRBS seed。
- 一个对象有信号而其他对象静音。
- bed 与对象使用可区分信号。
- 不同码率下的相关性、能量和串扰变化。

### 6.5 编码路径

- channel-based：**已有真实样本**。IMS profile 的两条 256 kbps 产物是 `b_channel_coded = 1` 的 `7.1_3/4/0.1`（`ch_mode = 6`），见 9.2j。默认 profile 仍不产生该路径——纯 bed、零对象的 `probe_bed_only` 也是 A-JOC（9.2e）；两者不矛盾，profile 不同而已。解析侧已能读出拓扑，**重建侧尚未实现**，故门禁按 `unsupported.coding_path` 跳过。
- direct-object：**现有编码链不产生该路径**，已由 M2 的 TOC 拓扑解析确认，见 9.2a。解析侧的分支覆盖只能靠构造码流（见 `topology.rs` 的 `recognises_direct_object_path`）；重建侧在取得能产生 direct-object 的编码器或合法样本之前，不安排验证工作，缺口保留在支持矩阵中。
- A-JOC full reconstruction。
- A-JOC core/full 行为差异。
- 不同 bitstream/presentation version，前提是编码工具链能够控制或已有合法样本。

## 7. 验证层级

### L0：容器与结构

精确比较：

- sample count、duration、sync frame 边界。
- `dac4`、bitstream version、presentation 数量。
- group/substream 拓扑和随机访问点。

### L1：元数据与时间线

精确或按规范量化比较：

- 对象/空间对象组数量。
- OAMD 码值。
- update offset、ramp duration 和状态继承。
- reset、seek 和 discontinuity 行为。

### L2：音频重建

容差比较：

- 最佳相关时延。
- 归一化互相关。
- 能量和频带误差。
- 对象间串扰。
- 静音泄漏和帧边界连续性。

### L3：受控渲染

测试工具可把场景输出送入固定、简单且版本冻结的诊断渲染器，比较 7.1.4 或其他固定布局结果。此渲染器仅用于验证，不进入解码器产品范围。

### L4：差分参考

已确认存在一个可访问**对象级**输出的外部参考解码器，详见第 9 节。它提供每对象 PCM 与每对象元数据，抽象层级与 `Ac4SceneFrame` 相同，因此可直接用作差分 oracle，而不必退化为渲染后混音比较。

参考实现不得与被测实现共享解析或 DSP 代码。参考解码器是参照物而非真理：三方（规范、本实现、参考解码器）不一致时以规范裁决。

## 8. A-JOC 的判定原则

A-JOC 会执行有损空间分组与对象重建，因此禁止把“解码对象 PCM 与原始 DAMF 轨道逐样本相等”作为通过条件。

实测进一步表明，输出对象与创作对象之间连**数量**关系都不成立（见 9.2）。因此对象匹配只能基于信号特征，索引、顺序和数量都不可作为对应依据。任何按位置配对再比较的测试写法都是错的。

可接受的 oracle 包括：

- 已知探针信号在预期输出组中具有最高相关性。
- 解码时延在预期范围内且跨帧稳定。
- 空间轨迹的量化和更新时间符合码流。
- 对象能量、串扰和固定布局渲染结果在冻结容差内。

容差必须按编码档位和案例类型记录，不能使用一个全局经验阈值。

## 9. 外部参考解码器

### 9.1 能力与获取方式

已验证一个外部 AC-4 参考解码器，可在无图形界面、无音频输出设备、无渲染器的纯命令行环境下产出**对象级**结果：

- 每个输出对象一路 PCM（单声道 32-bit float，48 kHz），每帧 2048 采样。
- 每个输出对象的种类标识（静态声道位或动态对象）与稳定的会话内序号。
- 每个输出对象的元数据项，其中位置以无符号 Q15 归一化三元组表示。
- 解码器声明的输出配置：最大动态对象数、最大元数据项数、元数据项长度与最小项偏移间隔。

它不暴露解码器内部状态，也不提供渲染结果。其宿主环境、模块标识与调用细节属于外部私有实现，记录在该项目自身的文档中，不进入本仓库；本项目只依赖上述可观测输出。

参考解码器的模块版本与哈希必须与编码工具同等对待，一并写入 `provenance.json`：同一码流在不同解码器版本下的输出差异，必须能够归因。

### 9.2 已确认的输出拓扑结论

对三个 AC-4 码流做过对照解码，均为 48 kHz、768 kbps：

| 码流 | 源构成 | 时长 | 解码帧数 |
|---|---|---|---|
| 自建探针 | 7.1.2 静音 bed + 1 个对象 | 6.0 s | 143 |
| 自建音乐样本 | 7.1.2 bed + 8 个创作对象 | 108.5 s | 2545 |
| 既有样本 | 来源无关 | 45.8 s | 1074 |

三者的解码帧数与各自源时长一一对应，可确认确实解码了不同码流。结论如下：

1. **输出容器固定为 21 个对象槽位（20 个动态 + 1 个静态），与源内容无关。** 三个码流的解码器声明配置与稳定帧拓扑逐字段一致，与源对象数、bed 布局、时长均无关。
2. **实际承载信号的槽位数取决于源内容，且远小于槽位总数。** 单对象探针只有一个槽位非静音，其余 20 个严格为零；18 路输入的音乐样本在有声段占用约 14 至 16 个槽位；既有样本占用 7 至 8 个。
3. **单个孤立对象不会被摊到多个槽位。** 探针以 −12 dBFS 正弦猝发在六个位置段依次发声，全部能量集中在同一个槽位上，其余槽位在全部 143 帧内保持零。这是稀疏场景下的观测，尚未确定槽位数接近上限时是否仍然保持分离。
4. **首帧声明的静态声道位不反映源 bed 布局。** 源为 7.1.2（两个顶部声道）的码流，其首帧仍声明四个顶部声道位，与其他布局的样本完全相同。首帧是解码器的初始拓扑声明，不能用于反推源布局。

关于编码路径需要特别说明：**从参考解码器的输出无法判定码流走的是 A-JOC 还是 direct-object。** 21 槽位是解码器的输出容器格式，不是码流的编码路径证据。该问题只能通过解析 TOC 与 presentation 结构回答，属于 M2 的工作。

### 9.2a 编码路径判定结果（M2，channel-based 一侧经 9.2j 修正）

TOC 拓扑解析完成后，该问题已有确定答案：**当时那条编码链只产生 A-JOC，不产生 direct-object。**

> **9.2j 已推翻其中的 channel-based 一半。** 换用 IMS profile 后同一母版产出的是 channel-based，`b_channel_coded = 1`。下文对 direct-object 的判定不受影响，对 channel-based 的「不产生」只在当时那套编码器配置下成立。

判定依据是 `ac4_substream_group_info()` 中的两个标志（`TS103190-2:v1.3.1:6.2.1.6`）：`b_channel_coded = 0` 排除声道编码，其后每个低频 substream 的 `b_ajoc = 1` 选中 `ac4_substream_info_ajoc()`。两个探针案例的全部 143 帧逐帧解析，无一例外。

同时解释了 21 槽位的来源：

| 解码模式 | 全带信号数 | LFE | 合计 |
|---|---|---|---|
| core（`n_fullband_dmx_signals`） | 9 | 有 | 10 |
| full（`n_fullband_upmix_signals`） | 20 | 有 | 21 |

A-JOC 的 LFE 由 `ac4_substream_info_ajoc()` 的 `b_lfe` 单独声明，不计入全带信号数（`6.3.2.10.8.2` NOTE 2）。因此 full 模式的 20 + 1 恰为参考解码器的 21 个输出槽位——**§9.2 结论 1 的容器尺寸来自码流声明，不是解码器的固定值。** 这与 §10 记录的「A-JOC 20.1，9.1 object core」一致，而后者来自独立工具。

core 与 full 两侧的 `bed_dyn_obj_assignment()` 均为 `b_dyn_objects_only = 1`，即两种模式下的信号全部是动态对象，没有床对象或 ISF 对象。源侧的 7.1.2 静音 bed 未以床对象形式出现在码流中。

判定不依赖任何外部工具，但有两项独立佐证：

- Bento4 从 `dac4` 读出的 codec string `ac-4.02.01.04`，其 `presentation_version = 1` 与 `mdcompat = 4` 同本实现解析的 DSI 一致；本实现再按 effective presentation ID 将 DSI 与逐位解析的首帧 TOC 闭合。DSI/TOC 顺序互换的构造测试确保该比较不依赖数组下标。12 份 A-JOC MP4 均为 1/1 匹配且零字段失配；两份 IMS Channel-based 的 DSI 还含保持不透明的 v2 envelope，暂只记录而不作闭合门禁。
- 每帧的 `payload_base` 与 `substream_index_table()` 必须与帧长自洽。两个案例的 substream 引用恰好覆盖 `{0, 1, 2}`（presentation → 0、OAMD → 1、A-JOC → 2），与索引表声明的三条尺寸一一对应。任何一位偏移都会破坏该排列。

上述检查已固化进 `scripts/cross_check.sh` 的拓扑门禁。

### 9.2b 随机访问、配置代次与序列计数器（M2）

**`b_iframe_global` 不足以判定随机访问点。** `TS103190-2:v1.3.1:6.3.2.1.3` 只要求每个 presentation 的**第一个** substream 无时间依赖；OAMD substream、presentation substream 以及 group 内其余 substream 各自还有独立的 `b_oamd_ndot`、`b_pres_ndot`、`b_audio_ndot`（`4.5.2`）。只满足前者的帧可以出声，但对象元数据可能仍在延续前序帧的状态——这正是本项目最不能接受的一类静默错误。

注意 `TS103190-1:v1.4.1:4.3.3.2.7` 对同一标志的表述是「所有 presentation 中的所有 substream」，与 Part 2 不一致。本实现按 Part 2 处理，因为它针对本项目精确覆盖的 `bitstream_version = 2`。该差异已记入规范可追溯性的未决问题。

实测结果：**7 个完整随机访问点，与容器 `stss` 声明的 7 个同步样本逐帧吻合，0 个「仅音频可起解」帧。** 两侧依据完全不同——一边是容器的同步样本表，一边是 TOC 内三类 ndot 标志的合取——因此这构成一条独立的一致性证据，已加入门禁。需要强调的是，规范并不要求二者一致，这只是当前编码器的行为；其他编码器可能产生 `stss` 标记但元数据仍有依赖的帧。

**解码延迟：声明为 5 帧。** `wait_frames` 传输码字为 6，按表 81 在 `frame_rate_index = 13` 下解释为 5 帧。这里有一个易错点：规范 `4.3.0` 规定后文引用该字段时指的是**解释后的值**而非位模式，且同一码字在 `frame_rate_index` 为 10…12 时代表的帧数翻倍。因此码字不应直接对外暴露，本实现用 `DecodingDelay` 承载解释结果，把 CBR（码字 0）与 VBR（码字 7）这两个非帧数的特殊含义与真正的帧数分开。

值得注意的是该流实际是 CBR（每帧恒定 4096 字节），按 `4.3.3.2.4` 本应声明码字 0。编码器给出的是保守的非零延迟，成因列入 9.6。

**配置代次为 1。** 全流完整规范化指纹不变。指纹包含 program ID、presentation/group 的固定配置与引用、声道模式、A-JOC 与 LFE 等字段，但将 ndot 清零，并排除 `payload_base`、substream 尺寸、EMDF 保留填充及 EMDF payload 的逐帧路由。因此逐帧信息不会误触发重配，声道模式或 A-JOC 配置改变也不会漏报。

DME 三条 A-JOC 流补出了原素材没有的正向分歧：携带 presentation 级 EMDF payload 时 `payloads_substream_index = 3`、原始索引表有 4 项，依赖帧不携带时只有 3 项。旧指纹据此让每条流产生 14 个配置代次与 135 个等待随机访问帧；规范化为固定 presentation/audio/OAMD/HSF 映射跨度后，三条流均回到 1 代、0 个首帧差异、0 个等待帧，并全部解析 143/143 帧。最小构造码流另锁定原始索引表 1 项与 2 项时指纹仍相等，确保门禁验证的是路由性质而不只是这三个文件名。

reset 状态机在首帧或配置/来源/解析状态变化后挂起重置，只在完整随机访问点执行。原两个案例与新增三条 DME 流均为 1 次初始 reset、0 个等待帧，结束时无挂起重置。

**`sequence_counter` 在当前向量中全程连续。** `4.3.3.2.2` 规定编码器最多计到 1020，`1020 → 1` 是正常回绕；前一值为 0 时表示 splice，其后任意非零值也是正常恢复。实测序列为：

| 帧 | 0 | 1 | 2 | … | 142 |
|---|---|---|---|---|---|
| `sequence_counter` | 1019 | 1020 | 1 | 递增 | 141 |

其中 1019 递增到 1020，再按规范回绕到 1，故 143 帧中的来源变化计数为 0。priming 和 edit list 另行描述呈现边界，不能从这段计数序列推断「前两帧是预热输出」。

由此得到一条状态机约束：**`sequence_counter` 不可用作帧序号或时间基准，它只是源变化的指示器。** 帧的定位一律使用容器 sample table 与 PTS。只有不符合正常递增、上述回绕或 splice 恢复的转移才上报来源变化，并挂起 reset 直到完整随机访问点。

### 9.2c OAMD 载荷与时间线（M3）

**OAMD 不在单一位置。** `TS103190-2:v1.3.1:4.8.3.4.2` 表 7 按 `b_ajoc` 给出各部分的所在层：

| OAMD 部分 | `b_ajoc` 为假 | `b_ajoc` 为真 |
|---|---|---|
| 配置数据 | `ac4_substream_info_obj` | `ac4_substream_info_ajoc` |
| 公共数据 | `oamd_substream` | `oamd_substream` 或 `ac4_substream_info_ajoc` |
| 时间数据 | `oamd_substream` | `oamd_substream` 或 `audio_data_ajoc` |
| 动态数据 | `oamd_dyndata_multi`，在 `oamd_substream` | `oamd_dyndata_single`，在 `audio_data_ajoc` |

由此得到一条实现依赖：**A-JOC 路径下逐对象的位置与增益不在 OAMD substream 里。** 它们位于 `audio_data_ajoc`，排在 `var_channel_element()`、`ajoc()` 与 `ajoc_dmx_de_data()` 之后（`6.2.3.4`），取到它需要频谱前端的比特解析能力。M3 当时因此等待 M4；该依赖现已解除，完整解析结果见 9.2h。表 7 同时说明该路径有两套动态数据：先 core 模式（`n_dmx_signals`）后 full 模式（`n_umx_signals`），解码器按出现顺序取用。

本阶段完成的是载荷侧 `oamd_substream()` 的完整解析，以及 OAMD 元素的语法实现（`object_info_block`、`object_basic_info`、`object_render_info`、`trim`、`bed_render_info`、`headphone`），后者对两条路径通用。直接对象的基本、渲染和附加字段保留原始码值；公共 `trim` 与 `bed_render_info` 当前只公开结构性字段，其余字段按语法消费。

**`byte_align` 是载荷边界自检。** `oamd_substream()` 以 `byte_align` 结尾（`6.2.2.4`），因此解析结束后的残余比特必须落在 0…7。两个案例共 286 帧全部解析成功，残余上界为 6 比特。这条检查能有效发现多数可变长分支错位，但等宽误读仍可能通过，不能单独证明字段语义完整；因此另以构造码流断言每个原始字段及跨帧合并结果。

实测结果（两个案例一致）：

| 项 | 值 |
|---|---|
| `oamd_common_data` 出现帧数 | 7 |
| `oamd_timing_data` 出现帧数 | 143 |
| 沿用前序块数的帧数 | 0 |
| `num_obj_info_blocks` | 恒为 1 |
| `block_offset_factor` | 恒为 0 |
| `ramp_duration` | 恒为 2 048 |
| `oamd_dyndata_multi` 块数 | 0 |

**公共数据只出现在 7 帧，与 `stss` 的同步样本逐帧同批。** CLI 按帧而非 group 计数，并直接统计两组成员关系的逐帧异或；门禁要求失配数为 0。这是继随机访问判定之后的第三条独立一致性证据，同样不是规范强制，而是该编码器的行为。

group 级的时间线由此明确：每帧在 `sample_offset + 32 × block_offset_factor = 0` 处一次更新，渐变时长 2 048 采样，恰为一帧。9.2e 曾根据 `mdat` 差异推测更密集的更新藏在 `audio_data_ajoc`；9.2h 的完整解析已经否定该推测：core/full 两侧的块数同样恒为 1，编码器把源端帧内四次更新降成了每帧一次。

`ramp_duration` 的表 95 有一处易错：表内最大值为 2 048，而 `6.3.9.3.8` 声明 `ramp_duration` 的范围是 `[0, 2047]`。二者不矛盾——该范围约束的是 11 比特直接编码的元素，不约束查表值。实现时若把表尾按 2 的幂外推会得到 8 192，与真实值相差四倍且不会被任何比特级门禁发现，因为查表不改变比特消耗。

**跨帧状态延续的应用。** `object_info_block` 的四个状态（`ALL_NEW`/`REUSE`/`PART_REUSE`/`DEFAULT`，见 `6.2.8.5`）由 `OamdState` 合并为每个对象的有效基本与渲染状态；增益内部复用及 `b_diff_pos_coding` 的三轴差分也会解析并应用。状态按物理 OAMD substream 隔离，更新失败不提交半成品；seek、配置变化、不连续和解析失败都会清空历史。规范要求 I-frame 的首块 `b_no_delta` 为真，此时语法上不传输 reuse 标志——单元测试同时覆盖自足首块、部分复用、差分位置及 reset 后拒绝复用。

`b_oamd_timing_present` 为假时 `num_obj_info_blocks` 不在本帧传输，只能沿用前序帧。本实现将其表示为显式的可选前序状态：确有非 A-JOC 对象需要动态数据而又无前序值时报 `TimingUnavailable`，不假定 0 块。

### 9.2d 拼接向量与 reset 状态机（M3）

M2 建立的 reset 状态机在两个探针案例上的计数全部为零:

```
配置代次              1
状态机来源变化        0
reset 事件            1        ← 只有 ResetReason::Initial
等待随机访问帧        0
```

也就是说 `SourceChange`、`ConfigurationChange`、`WaitForRandomAccess` 与 OAMD 的清史逻辑**对真实数据的覆盖是零**。这些恰恰是每个播放器都会走的路径(seek、拼接、换源),而单一来源、单一配置的向量永远走不到。

`scripts/make_splice.py` 把两条已编码轨道重新定界为一条 `Annex G` 裸流,在指定帧处切换来源。它不改写任何一帧的内容,只重排。`4.3.3.2.2` 定义 `sequence_counter` 的用途正是「检测流来源的非受控变化,例如拼接操作」,因此这是在制造该字段被设计来检测的场景,不是伪造数据。

期望值由容器 sample table 与计数器算术导出,判定值由 Rust 侧的比特级 TOC 解析给出,两者没有共同来源。门禁为 `scripts/splice_check.sh`。

**错位拼接的实测结果:**

| 项 | 期望 | 实测 |
|---|---|---|
| 来源变化 | 1 | 1 |
| reset 事件 | 2 | 2 |
| 等待随机访问帧 | 21 | 21 |
| 结束时仍等待 | 否 | 否 |

21 帧等于拼接点到下一个完整随机访问点的距离,两侧独立算出同一个值。

**同下标拼接暴露了一个更重要的事实:它完全不可检测。**

两条流出自同一编码器、同样长度,`sequence_counter` 因而逐帧同步。在第 60 帧处从 A 切到 B 的第 60 帧,边界两侧的计数恰好衔接,状态机报告的来源变化为 0、等待帧为 0,与一条干净的流毫无区别。配置指纹同样不变——两条流的编码配置相同。

由此得到两条明确结论:

- **`sequence_counter` 不是充分的拼接指示器。** 它检测的是计数不连续,不是来源变化本身。计数恰好衔接时,一次真实的换源不留任何痕迹,解码器会把前一来源的 A-JOC 与 OAMD 状态直接带过边界。
- **配置指纹也不是。** 相同编码配置的两条流,指纹按定义相同。

因此安全的起解策略只能是:**只在完整随机访问点重建状态,并把容器层的不连续信号作为独立输入**,而不能依赖码流内的任一单一字段。这条约束记入 M3 的状态机设计,`OamdState` 与 `TopologyStateMachine` 都提供显式的外部不连续入口(`mark_discontinuity`、`reset`),就是为此。

这两个变体同时也是裸流路径的首个完整拓扑与 OAMD 用例。此前裸流只解析到 TOC 前置字段;现在两条定界路径运行同一套巡检,唯一差别是裸流没有 `stss`,相关比对按 `None` 跳过而不是默认记为一致。

### 9.2e 码率梯度与元数据密度实验（M3，结论经 M4 修正）

四个新案例由 `scripts/build_vector.sh` 跑完整链路生成，回答了 9.6 中的三个未决问题。整条链已验证可逐字节复现：重跑 `probe_axes_single_object` 得到的 DAMF 三件套、ADM BWF 与 `mdat` 哈希全部与既有记录一致。

**上混信号数与码率无关。** 同一条 ADM BWF 编码到三个档位：

| 码率 | `n_fullband_dmx_signals`（core） | `n_fullband_upmix_signals`（full） | 对象总数 |
|---|---|---|---|
| 256 kbps | 5 | 20 | 21 |
| 448 kbps | 7 | 20 | 21 |
| 768 kbps | 9 | 20 | 21 |

随码率变化的是 **core 下混宽度**，full 模式的对象数固定为 20 加 LFE。9.6 中「20 个上混信号是码率档位决定还是固定配置」由此关闭：是固定配置。三个档位的 `b_ajoc` 均为 1，`b_static_dmx` 均为假，`md_compat` 均为 4，解码延迟均为 5 帧。**低码率不产生 direct-object**，该假设被排除。

**补充 1024 与 1500 两档后，下混宽度的阶梯是 `256→5`、`448→7`、`768→9`、`1024→9`、`1500→11`。** 768 与 1024 落在同一格。同一当前工具、同一母版、同为 768 kbps 的受控导出中，Logic 与 DAR 后端都给出 9 路 core；这支持项目把同码率产物归入同一行为档。后端不是测试矩阵的一维，其指纹只用于溯源，不用于比较编码器版本。

**这套向量测不出码率差别，因为素材太容易编。** 用真实 ADM 母版（42 声道、157 秒的音乐内容，不入库）与合成向量同档对照容器样本的实际占用：

| 素材 | 后端 | 768 | 1024 | 1500 |
|---|---|---|---|---|
| 真实母版：占用率 / 等效码率 | Logic | 95,32 % / 732,1 kbps | 94,41 % / 966,7 kbps | — |
| 真实母版：占用率 / 等效码率 | DAR | 95,33 % / 732,1 kbps | — | 93,31 % / 1 399,7 kbps |
| 保留的合成向量：占用率 / 等效码率 | Logic | 12,44 % / 95,6 kbps | — | — |
| 保留的合成向量：占用率 / 等效码率 | DAR | — | — | 9,22 % / 138,2 kbps |

「占用率」是容器样本去掉尾部零字节后的长度占样本槽的比例；等效码率按 AC-4 媒体时长折算。受控真实母版四档使用 93,3 %–95,3 % 的预算，保留的合成向量只使用 9,2 %–12,4 %。旧的合成 1024 产物已经撤回，其粗略统计不混入这张统一口径表。

数值、命令、源母版与四份 AC-4 基本流哈希、统计口径及限制单独保存在[真实母版码率观察记录](experiments/real_master_bitrate_observation.json)。媒体不入库，因此它是有本地指纹的受控观察，不是可由仓库独立复现的回归基线。

由此有三条：

- **合成向量上 768 与 1024 的核心带 PCM 逐位相同**（`d17a8f0e…`），143 个样本去尾零后长度全同，其中 73 个逐位相同、70 个只差 `ac4_toc()` 里 `wait_frames` 之后那 2 个保留比特（解析器读掉即丢，故 trace 完全一致）。这不说明 1024 是空档：同一 Logic 后端的受控真实母版上，`scale_factor_bands` 为 `1 669 362→1 705 241`，`scaled_lines` 为 `37 200 948→37 206 452`，码率确实生效。
- 因此 `probe_axes_single_object` 不保留 1024 档：它与 768 解码结果逐位相同，回归价值为零。`case.json` 声明 `[768, 1500]`。
- **加档位能扩展配置与拓扑边界，但不能补足素材复杂度覆盖。** 1500 档把 core 宽度从 9 扩到 11；依赖复杂内容才出现的高码率行为仍然必须换素材才能覆盖。

**音调生成的命中密度在当前母版上不随码率单调增加。** 只在同一后端内比较码率：

| 后端 | 低档 | 高档 | `aspx_add_harmonic` 命中帧数 |
|---|---|---|---|
| Logic | 768 | 1024 | 13 → 13 |
| DAR | 768 | 1500 | 1 150 → 1 087 |

Logic 与 DAR 在 768 kbps 上的音调计数不同，因此跨后端的 `13→1 150` 不能拿来归因码率；按项目口径，后端差异也不扩成版本比较轴。合成向量上的 `768→15`、`1024→15`、`1500→0` 同样只是素材与所用后端的联合观测，那个 0 不能读成「高码率不需要合成正弦」。

四份受控真实母版产物的 `aspx_balance_frames` 与 `aspx_interleaved_frames` 都为 0。这里的「未观察到」只限定当前母版、四个档位与工具配置，不外推到编码器版本。

**源端帧内多次更新改变了编码结果，但没有被逐次保留。** 案例 `probe_subframe_updates` 每 512 采样一次位置事件，即每个 2 048 采样的 AC-4 帧四次。逐层核对：

- DAMF 元数据：192 个事件。
- 规范化后的 ADM BWF：192 个 `audioBlockFormat`，`rtime` 间隔 `00:00:00.01067` 即 512 采样。更新完整保留。
- AC-4 的 `oamd_substream`：`num_obj_info_blocks` 仍恒为 1，`block_offset_factor` 恒为 0。

对照案例 `probe_subframe_control` 除位置事件降到每帧一次外完全相同——对象音频逐字节相同，因为位置只是元数据。两者的 `mdat` **不同**，高密度版本每帧多用 6.5 字节。这个差异只能证明源端密度影响了编码结果，不能证明 192 次更新都以独立时间块进入码流。

M4 完整解析两处 `oamd_dyndata_single()` 后得到最终结论：八条流的 core/full `num_obj_info_blocks` 都恒为 1；`probe_subframe_updates` 的 50 帧只记录到 43 次逐帧位置变化。编码器确实吸收了高密度输入，但把时间粒度降为每帧一次，没有留下可恢复的帧内四次更新时间线。见 9.2h。

**`rampLength` 被编码器完全忽略。** 案例 `probe_ramp_lengths` 让源端逐段声明 0、512、1536、32、1024、1600、1920、2048、256、480 采样的 ramp；对照案例 `probe_ramp_control` 轨迹相同但 ramp 全为 0。两者的 `mdat` **逐字节相同**。

与上一条形成明确对照：位置密度改变了码流，ramp 长度没有。因此 9.6 中「`ramp_duration` 恒为 2 048 是码率所致还是编码器固定策略」关闭为：**编码器的固定策略，与源端声明无关，也与码率无关。** 这意味着 `ramp_duration_code` 的 `0b00`/`0b01`/`0b10` 三个分支与 `ramp_duration_table` 的其余条目，在本编码链下无法由真实码流覆盖，只能依靠构造码流。

9.2i 补上了这条结论的另一半：编码器并非不做平滑，而是**用自己固定的一阶平滑取代了源端声明**——写进码流的位置本身已经过滤，`ramp_duration` 再恒取整帧。源端的 `rampLength` 因此无处可去。

**源帧率对 AC-4 无影响，`frame_rate_index` 10…12 不可达。** 以 23.976、25、29.97 fps 各生成一次母版，规范化后的 ADM BWF 互不相同（帧率写在其中），但四条 AC-4 的 `mdat` **逐字节相同**，`frame_rate_index` 一律为 13。AC-4 的该字段描述的是音频帧率（48 000 / 2 048），不是源母版的视频帧率；编码器也未暴露相应选项。

因此 `frame_rate_multiply_info()`、`frame_rate_fractions_info()` 的非空分支，以及 `frame_rate_factor > 1` 时 `b_audio_ndot` 的重复读取与表 81 解码延迟翻倍，在本编码链下**无法由真实码流覆盖**，只能依靠构造码流。这三个案例因与既有向量产出完全相同的码流而未保留。

**纯 bed、零对象仍然是 A-JOC，改素材触不到 channel-based。** 案例 `probe_bed_only` 为 7.1.2 十声道各一个可区分频率、不含任何对象的母版——这是最可能触发声道编码的输入。实测 `b_channel_coded = 0`、`b_ajoc = 1`，`bed_dyn_obj_assignment` 给出 `bed = 0, isf = 0, dynamic = 20`，与含对象的案例毫无区别。

至此三条编码路径在**默认 profile 内**的可达性全部确定：默认 profile 无条件产生 A-JOC，direct-object 与 channel-based 都只能靠构造码流做分支覆盖，缺口保留在支持矩阵中。

> **「无条件」当时是过度外推。** 这组实验只动了码率与素材，没有动 profile；换到 IMS profile 就是 channel-based，见 9.2j。本节其余结论不受影响——它们都是默认 profile 内部的对照。

该案例的 768 kbps 档未采用：编码器对这份全声道持续发声的素材实测得 770 510 bps，未通过其自带的码率校验；256 与 448 两档正常。素材本身对 M6 的 bed 重建与串扰测量仍有价值，因此保留这两档。

**顺带修好一个门禁缺陷。** 新案例的时长不是整毫秒（81 920 采样 = 1 706.67 ms），暴露出交叉核对拿采样精确值去比 MediaInfo 的毫秒精度值，回算得 81 936 而误报不一致。既有两个案例恰好都是整秒，因此从未触发。现在两侧统一化到毫秒再比。

### 9.2f 音频 substream 框架与 metadata（M4 首个增量）

`ac4_substream()` 以 `audio_size` 开头。`TS103190-1:v1.4.1:4.3.4.1` 规定它是 `audio_data` 连同其后 `fill_bits` 与 `byte_align` 的字节数，**不含 `metadata` 及最后的 `byte_align`**，并附 NOTE：「这使解码器无需解析音频数据即可直接访问 metadata」。本增量正是走这条规范自带的捷径，因此不解码音频，也不触及频谱前端。

**判定条件是落点。** substream 的总长由 `substream_index_table()` 独立声明，`ac4_substream()` 以 `byte_align` 结尾，所以「跳过 `audio_size` 字节 → 解析 `metadata()` → 对齐」之后必须**恰好**落在 substream 末尾。这比 OAMD 的 `byte_align` 残余强得多：那里只约束到 8 比特以内，这里是整字节级的精确等式。八条码流全部通过，0 次落点失败。

帧 0 的算术可直接核对：索引表声明 substream 2 为 948 字节 = 头部 2 + `audio_size` 943 + metadata 3。

**`sus_ver` 在 `bitstream_version = 2` 下恒为 1**（`6.3.2.5.4`：不满足 `bitstream_version == 1` 的两个分支都直接赋 1）。这一条决定了两件事：

- `basic_metadata` 的 `dialnorm_bits` **只在 `sus_ver == 0` 时传输**，因此本项目的码流里根本没有 dialnorm。实测 `dialnorm_frames = 0`，已入门禁。
- `metadata()` 中的 `drc_frame()` 同样只在 `sus_ver == 0` 出现。实测 `tools_metadata_size` 恒为 **1 比特**，即只有 `dialog_enhancement` 的 `b_de_data_present = 0`。

由此得到一条与解码器无关的码流事实：**本项目的码流不含任何响度或 dialnorm 元数据。** `basic_metadata.dialnorm_bits` 在 `sus_ver == 1` 下根本不传输，实测 `b_substream_loudness_info = 0`，连 `substream_loudness_bits` 也没有。这条结论独立成立，任何涉及响度的推断都不能把它当作来源。（它原本是为追查一个「15.0 dB 固定衰减」而查的；那个现象已于 2026-08-18 撤回，见 9.6。上面的码流事实不受影响。）

其余实测：`b_dialog = 0`、`b_channels_classifier = 0`、`dc_block_on = 1`，metadata 区段恒为 2 至 3 字节。A-JOC 的 `channel_mode` 未设定（`6.2.2.2` NOTE 2 规定此时视为负值），`basic_metadata` 与 `extended_metadata` 中所有以它为条件的分支都不成立；声道编码 substream 会走这些分支，本实现显式拒绝而非猜测。

**这个首个增量当时尚未解锁逐对象位置。** 表 7 规定 A-JOC 的 `oamd_dyndata_single` 位于 `audio_data_ajoc` 内部，跳过音频数据的同时也跳过了它。后续 M4 已完成 `var_channel_element()` 到 `audio_data_ajoc()` 的全链路解析，结果见 9.2h。

### 9.2g 频谱前端的实际分支分布（M4）

`audio_data_ajoc` 紧跟在 `audio_size` 头部之后（P2 `6.2.2.2`），因此 `b_some_signals_inactive` 与 `var_codec_mode` 无须解析音频即可读出。用临时探针在三档码率上读取：

| 码流 | `n_dmx` | `b_isodd` | `n_pairs` | `var_codec_mode` | `companding_control` |
|---|---|---|---|---|---|
| 768 kbps | 9 | 1 | 4 | A-SPX | 否（条件为 ≤ 5） |
| 448 kbps | 7 | 1 | 3 | A-SPX | 否 |
| 256 kbps | 5 | 1 | 2 | A-SPX | 是 |

三档均为 `b_lfe = 1`、`b_some_signals_inactive = 0`，`var_codec_mode` 在全部帧上恒为 1（表 77：`1 = A-SPX`）。

**结论：SIMPLE 这条捷径在本编码链上不存在。** 落到 `audio_size` 必须同时具备 ASF（`4.2.8`）、A-SPX（`4.2.12`，且需 `5.7.6.3` 的频带表推导）与 A-JOC（P2 `6.2.5`）。这比 M4 立项时的估计大。

两处减负：

- `two_channel_data()` 与 `three_channel_data()` 中 `sf_info(ASF, 0, 0)` 写死 ASF，SSF（`4.2.9`，算术编码 + 附录 C 表）只可能出现在 `mono_data(0)` 的 1 比特 `spec_frontend` 上；当前解析器在选中该分支时显式拒绝；
- 码率梯度已覆盖 `companding_control` 的两侧，无需新造向量。

**实现期间没有中间门禁。** `audio_data_ajoc` 之后是 `fill_bits`（VAR）再 `byte_align`，因此最终规范条件只是「不超过 `audio_size` 且余量为合法填充」，而非精确等式——比 9.2f 的落点判定弱。当时只能靠取值域自洽（变换长度落在表 B.1 内、`max_sfb` 不超过该变换长度的 `num_sfb`、`sect_cb ≤ 11` 等）逐层推进。完成后的真实向量恰好都不写额外填充，故 9.2h 可将 `fill_bits < 8` 固化为当前编码链的经验门禁；它不是规范对任意编码器的要求。

### 9.2h A-JOC 音频数据全链路解析（M4）

ASF 成帧与熵编码、声道元素、A-SPX 九个语法元素、`var_channel_element()`、A-JOC 矩阵、对话增强/床信息及 `audio_data_ajoc()` 已串到 `ac4_substream()`。八条实测流共 **568 帧全部解析成功**，`fill_bits` 均小于 8，只剩末尾 `byte_align`；`scripts/audio_check.sh` 将帧数、物理 substream 数、状态失败和落点一起作为门禁。

两处 `oamd_dyndata_single()` 会写出带 `object_index` 与 `block_index` 的块，core/full 分别持有状态。状态先在副本上逐块解算，两批都成功后才一起提交；full 失败时 core 状态、位置计数和时间线均不得提前更新。构造测试保留了帧内多块的通用语义，但现有编码链的真实向量两侧块数均恒为 1。

位置探针同时完成了轴映射标定：X 与 Z 同向，Y 反向；中心量化码为 `(31, 31, 0)`，六段极值与母版意图逐段对应。详细码值和帧边界见实施路线图 M3。

### 9.2i 母版轨迹的自动比对（M3）

`scripts/trajectory_check.py` 把 9.2h 标定的轴映射固化成回归门禁：由 `case.json` 的分段位置生成母版逐帧轨迹，与 trace 解出的逐对象轨迹逐轴比对。媒体选择同样由 manifest 驱动：默认 `encodes` 与 `dme_ac4` 声明的 A-JOC 产物必须存在并逐条检查；`dee_ims` 声明的 channel-based 产物会具名跳过；目录里无法归入任一作业的 M4A、重复输出名或缺少已声明的 A-JOC 产物都 fail-closed，防止新后端静默绕过轨迹门禁。

**判据不能是逐帧相等，因为编码器对位置做了一阶平滑。** `probe_ramp_control` 每 4 096 采样在 ±1 之间跳变，段边界正好落在帧边界上，解出的 x 是稳定的四帧周期：

| 母版阶跃 | 解出的逐帧码值 | 每帧走完的剩余距离 |
|---|---|---|
| 62 → 0 | 11、2 | 81.7 %、81.8 % |
| 0 → 62 | 51、60 | 81.7 %、81.8 % |

`probe_axes_single_object` 的 0 → 62 阶跃解出 `45、59、61、62`，中间一步同为 82.4 %；首步偏小（72.6 %）是因为该段起点 48 000 采样落在帧 23.44，第一帧只经历了 0.56 帧的时长。段长不足时位置根本追不上母版就已换段，这正是 `probe_ramp_*` 的 x 轨迹永远在 `2…60` 之间摆动、从不到达 `0` 或 `62` 的原因。

因此门禁用两条互补判据：

- **形状**——实测与母版逐轴的 Pearson 相关系数不低于 0.9，滞后在 6 帧内自动对齐；母版该轴恒定时改判实测是否同样恒定。
- **到位**——段长不短于 8 帧时要求期望码值精确出现，平滑此时有充足时间收敛。

两条缺一不可：把满量程从 62 误作 63 时相关系数仍是 1.000，只有「到位」判据抓得住；反之滞后一帧的错位只有相关性判据抓得住。注入 x/y 互换、y 不反向、z 符号反转、满量程 62→63 与 15→16，六个案例全部报错。

静音期不参与比对——编码器会把不发声的对象泊到原点角 `(0, 0, 0)`，那不是母版声明的位置。

**六个案例的动态对象全部落在同一个槽位：full 侧的对象 1。** 脚本不假设母版对象下标与输出槽位相同，而是逐槽位取相关性最高者；结果一致落在对象 1，与 9.6 中 A-JOC identity 的未决问题相互印证，但样本都是单对象场景，不足以推广。

`probe_axes_single_object` 现在一次检查默认 768K/1500K 与三条 DME，共 5 个 A-JOC 产物；它们都匹配 substream 2 的 full 对象 1，三轴相关系数均为 1.000、最佳滞后均为 3 帧，六个长段均精确到位。两个 IMS 256K 产物按上述 manifest 分类明确排除，因为其 `b_channel_coded = 1`，不存在可与 full A-JOC 对象槽位等价比较的轨迹。

### 9.2j IMS profile 产出 channel-based（M4）

**9.2a 与 9.2e 的「现有编码链不产生 channel-based」已被推翻。** 同一条 `probe_axes_single_object` 母版，改用 IMS profile 后端导出的两个 256 kbps 产物走的都是声道编码：

| 观测项 | `master_ac4_ims_256K` | `master_ac4_ims_legacy_256K` | 对照：`master_ac4_768K` |
|---|---|---|---|
| `b_channel_coded` | 1 | 1 | 0 |
| 编码路径 | channel_based | channel_based | ajoc |
| substream 种类 | `channel` | `channel` | `ajoc` |
| `ch_mode` | 6（`7.1_3/4/0.1`） | 6（`7.1_3/4/0.1`） | — |
| 对象数 | 0 | 0 | 21 |
| OAMD substream | 无 | 无 | 有 |
| presentation 数 | 1 | 2 | 1 |
| `md_compat` | 0 | 0 | 4 |
| 解析帧数 / 完整随机访问点 | 141 / 6 | 141 / 6 | 141 / 7 |

两个文件哈希不同，不是同一份产物的重复登记。差别在 presentation 层：`legacy` 变体多一个 `presentation_version = 1` 的 presentation，把**同一个** substream（索引同为 1）描述成 stereo（`ch_mode = 1`）；非 legacy 只有一个 `presentation_version = 2` 的 presentation。两者的 group 都是 `b_channel_coded = 1`，音频侧没有第二份数据。

**这条结论的作用范围要说清楚。** 它推翻的是「这套工具链无论怎么配都只出 A-JOC」，不是 9.2a 的判定方法，也不涉及 direct-object——后者至今没有任何真实样本。9.2e 里「低码率不产生 direct-object」「纯 bed 零对象仍为 A-JOC」两条实验本身仍然成立，它们当时的编码器配置没有变；变的是**配置空间比当时探到的更大**。这也是 9.2e 已经写过的那条限制的一次兑现：结论只限定当时的母版与工具配置，不外推到别的 profile。

**`ch_mode = 6` 第一次有了真实样本。** 落在 `5_X_channel_element`/`7_X_channel_element` 的取值区间，此前只有构造码流的分支覆盖（§6.5）。重建侧尚未实现声道编码路径，因此这两条向量目前解不出声道；`export-core-pcm` 为此报 `unsupported.coding_path` 而不是 `internal.invariant_failed`——码流没问题，是实现有缺口。`scripts/decode_check.py` 据此逐条列名跳过，规矩见规范可追踪性 5.19d：**已进基线的条目永远不许跳过**，且一条都没真正解码时整次门禁失败。

### 9.2k core 是扬声器形状的对象网格，不是声道布局（M4）

先把规范边界钉死。P2 `4.8.3.1` 与表 6 条件 3.1 只在 full decoding mode 使用 A-JOC；core 模式绕过 A-JOC 上混，采用较少的下混对象。`4.8.3.4.2` 又规定 `b_static_dmx = 0` 时第一份 OAMD 专供 core、第二份专供 full。只有 `6.3.2.8.3` 的 `b_static_dmx = 1` 才把 core signal 定义成静态 5.0/5.1 bed；当前九条 A-JOC 流全部为假，伪码 26 因而给出 `pres_ch_mode_core = -1`。所以严格答案是：**当前 core 没有规范声道模式，它由带独立 OAMD 的对象组成。** `5.8.2.4` 又把 core DE 的 `x_ch` 明确定义成 `5.7.2.1` 的 `Qin_AJOC`，因此 Pseudocode 14a 不只是 full 上混的输入置换，也是 core 对象 essence 的顺序。

编码器仍然表现出非常规则的行为。把第一份 OAMD 以 core 模式导出后，四档全带对象固定在以下坐标网格；LFE 另算一路：

| 码率 | 全带对象数 | 固定坐标集合的形状 | 加 LFE 后的直观类比 |
|---|---:|---|---|
| 256 kbps | 5 | 前方 L/R/C + 后方 L/R | 5.1-like |
| 448 kbps | 7 | 上述 5 点 + 顶部中段 L/R | 5.1.2-like |
| 768 kbps | 9 | 5 点 + 顶部前/后 L/R | 5.1.4-like |
| 1500 kbps | 11 | 前方 L/R/C + 侧/后 L/R + 顶部前/后 L/R | 7.1.4-like |

这里的 `*-like` 是对坐标形状的简称，**不是码流传输的声道标签**。九条 A-JOC 流的所有 core 对象在全时长内位置都不动；另外五条 768 kbps 探针与 `probe_axes_single_object` 得到逐对象完全相同的 9 点网格。因此这是当前编码器按 core 宽度选择的稳定模板，而不是某一条母版的偶然位置。

`probe_bed_only` 说明 BED 的作者侧类型在这里已经消失。其 core/full 两份 `bed_dyn_obj_assignment()` 都是 `dynamic_only`；full 侧对象 1–9 的位置分别覆盖源 7.1.2 BED 的 L、C、Lss、R、Lrs、Rss、Lts、Rrs、Rts，余下对象保持默认位置。换句话说，**源 BED 通过动态对象的静态位置模板表达，不再是 BED 类型。** core 再把这套内容压到 5 或 7 个固定对象。

多频正弦把这种压缩直接变成可测的混合矩阵。对 A-SPX 后的 `q0…qN` 按源频率投影，并先执行 P1 `5.3` 的 MDCT 声道矩阵后，左右源严格落到成对对象：L/R 为 `q0/q1`，左/右侧后与顶部折叠到 256 档的 `q3/q4`；448 档新增高度对后，Lts/Rts 各自 100 % 落到 `q5/q6`。LFE 始终单独一路。这里仍不是源扬声器编号：Lss 与 Lrs 同落 `q3`，Rss 与 Rrs 同落 `q4`，说明多个作者侧 BED 角色被烘焙进同一固定 core 对象。

单移动对象给出另一半。core OAMD 的网格仍全程静止，1 kHz 音频却随源位置在固定对象间重分配：X-min/X-max 各自 100 % 落到 `q3/q4`；Y-min 在 9 路 core 约等功率落到 `q3/q4`，11 路 core 改落新增的 `q9/q10`；Z-max 在两档都等功率分到四个高度对象 `q5…q8`。相同码流的 full 侧则由对象 1 的 OAMD 位置移动。也就是说：**full 尽量保留创作对象身份与运动，core 把场景烘焙成较低分辨率的固定对象网格。**

### 9.2l 固定 core 网格的直接扬声器 CAF（M4）

9.2k 不授权把任意 core 叫作声道，但给出了一个可判定的严格子集：若第一份 OAMD 在
完整呈现时间线中逐事件精确等于已记录的 5/7/9/11 点整数模板，对象始终活动、默认
0 dB 且没有 width/zone/screen/depth/distance/divergence 等渲染修饰，则让对象 renderer
把每个点送入同位置扬声器不再引入位置插值。`export-core-caf` 据此先验证 OAMD，再把
`Qin_AJOC` 与独立 LFE 直接装入 CoreAudio layout tag；只看码率或路数不够，任何位置变化
或修饰都返回 `mapping.unsupported`，也没有强制布局参数。

严格门禁还覆盖两个容易被“目标状态正确”掩盖的入口。第一，可见区起点事件若带非零
`ramp_duration`，必须从 preroll 中找到同一对象的前态，并让前态也通过同一固定网格判据；
缺前态或前态处于另一位置/增益时拒绝，不能把渐变的目标端点当作整段恒定。第二，所选对象
的 OAMD common 必须一致且 `common_conflict = false`，自定义 screen、bed distribution/render
和带自定义系数的 trim 均拒绝。当前编码链固定写规范保留的 `warp_mode = 0b11`，但九个配置
恰为无自定义系数的 `default/disabled` 固定组合；直接网格只精确白名单这一实测 profile，
并未把 `0b11` 外推成规范位置变换。其他保留组合仍 fail-closed。

真实向量的 release smoke 结果如下；布局名和括号内顺序均由 macOS `afinfo` 从生成 CAF
的 `chan` chunk 读回，不是 CLI 自述：

| 输入 | PCM 帧 | CAF/`afinfo` |
|---|---:|---|
| `probe_bed_only` 256K | 96 000 | 6 ch，5.1 (`L R C LFE Ls Rs`) |
| `probe_bed_only` 448K | 96 000 | 8 ch，5.1.2 (`L R C LFE Ls Rs Ltm Rtm`) |
| `probe_axes_single_object` 768K | 288 000 | 10 ch，5.1.4 (`L R C LFE Ls Rs Vhl Vhr Ltr Rtr`) |
| `probe_axes_single_object` 1500K | 288 000 | 12 ch，7.1.4 (`L R C LFE Ls Rs Rls Rrs Vhl Vhr Ltr Rtr`) |

前三档的 interleave 分别是 `q0 q1 q2 LFE q3 q4`、再追加 q5/q6、再追加 q7/q8；
7.1.4 必须写 `q0 q1 q2 LFE q3 q4 q9 q10 q5 q6 q7 q8`，因为 Apple 把 rear pair
排在四个高度槽之前。端到端 768K 回归直接解析 `desc`/`chan`/`data`，固定 tag
`(195 << 16) | 10`、288 000 帧和 JSON 逐轨来源；构造事件另覆盖四套模板、起点 ramp
前态、common profile、原子 no-clobber 与严格拒绝面。

样本写 Float32 LE 并固定乘 `2^-15`。该乘法只是内部 `±32768` 到 PCM 单位的换算，
不含节目相关扫描：没有 sample peak、true peak、响度归一化、限幅或削波，超过 `±1.0`
的有限样本保留。外部处理后的 CAF 必须保留或重写原 `chan` tag。这个出口因此适合当前
模板的试听/后处理，不替代 9.2k 的规范结论，也不扩展到其他编码器的动态 core。最终发布
在同目录对已同步临时文件建立 hard link：目标若已存在由文件系统原子拒绝，随后才移除
临时链接，不再留下“检查后覆盖式 rename”的竞态窗口。

### 9.3 参考解码器的能力边界

**曾经的结论：参考解码器在纯命令行路径下不提供位置元数据。** 对探针码流的 143 帧 × 21 对象共 3003 个组合逐一检视，元数据容器全部可获取，但其中仅 1 个非空，最大项数为 1。原因是那条路径只在存在元数据写入方时才输出位置命令，而写入方必须由音频端点提供。

**该结论已于 2026-08-17 被推翻，限定条件是「那条路径」。** 换一条本地适配路径后，逐块位置元数据可以取得，并已用于对照：DRP 4.3.0.19350 arm64 runtime 产出的两份 AXML 与记录哈希一致；664 个点、1992 个坐标全部通过逐轴绝对差 `< 1e-9` 的容差判据，实测最大绝对差为 `4.838629497072588e-13`。个人适配工具的名称与调用路径不入库。见 [ROADMAP](ROADMAP.md) M3 与[实验记录](experiments/reference_decoder_position_crosscheck.json)。因此定位更新为：**它既是对象级 PCM 的 oracle，也是元数据的 oracle。**

**「参考解码器」这个词在本章内指两个不同的东西，读的时候必须分开。** 本节 2026-08-17 的对照用的是 DRP 4.3.0.19350 arm64，那是厂商权威 runtime；而 9.4 的标定表测于 2026-07-26，用的是当时唯一走得通的一条**兼容性解码**实验路径，此后从未在 DRP 上重测。凡涉及 PCM 电平与时延的数字都出自后者，**不带 DRP 背书**。

这是一次典型的「能力判断绑死在当时用的那条调用路径上」。原结论对它测的东西没说错，错在把「这条路走不通」写成了「它没有这个能力」——和 `CLAUDE.md` 里「不确定就写不确定」是同一条教训的另一面。

**但下面这段方法论不变，而且正是本次对照遵循的：** 位置正确性的权威来源仍是码流中的 OAMD 码值，验证链条为「案例描述中的已知位置 → 编码器量化 → 本实现解析出的 OAMD 码值」，全程不经过参考解码器。参考解码器输出的归一化坐标是经其自身语义解释后的第三套坐标系，只能作为交叉验证，不能替代对码值的精确比较。本次对照因此没有引入新的自由度——轴映射沿用 ROADMAP M3 由母版意图标定的那一组常数，参考解码器给出的是第二个独立来源的确认，不是映射的来源。

### 9.4 探针标定结果（来自早期兼容性解码路径，**未经 DRP 复核**）

**本节全部数字的来源不是 9.3 认定的那个 oracle。** 它们测于 2026-07-26 的初始提交，用的是当时唯一可走通的一条**兼容性解码**实验路径；DRP 4.3.0.19350 arm64 直到 2026-08-17 才接通（见 9.3），此后本节从未重测。9.3 把「参考解码器」升格为对象级 PCM 与元数据的 oracle，而本节沿用同一个词——**两者指的不是同一个东西**，读到这里不要把 9.3 的权威性顺延过来。

因此下表描述的是**那一个兼容性解码器的输出行为**，不是 AC-4 的规范行为，也不是 DRP 的行为。它作为「当时观察到什么」仍然有效，作为标定常量则**尚未成立**。

案例 `probe_axes_single_object`（7.1.2 静音 bed + 单对象，1 kHz 正弦猝发 −12 dBFS，六个位置段，768 kbps）经该路径解码并逐对象落盘后测得：

| 特性 | 实测 | 说明 |
|---|---|---|
| 对象隔离 | 静音槽位峰值严格为 `0.0` | 非近似零；bed 与未使用槽位无任何泄漏 |
| 信号集中度 | 全部能量位于单一槽位 | 其余 20 个槽位在全部 143 帧内为零 |
| 解码时延 | 4451 采样（92.73 ms） | 六段起点一致，抖动仅来自淡入沿的阈值判定 |
| 频率还原 | 1000.3 Hz（源 1000 Hz） | 猝发段 FFT 主峰 |

静音行为存在分化，落盘与比较逻辑都必须据此设计：**未被占用的槽位输出严格 `0.0`，而承载低电平内容的槽位输出极小非零值。** 单对象探针的 20 个空闲槽位在全部 143 帧内严格为零；真实音乐样本的渐入段虽然听感为静音、峰值低于千分位，其采样却有约 99.5% 非零。

槽位占用是**逐帧动态**的，而非全流固定。案例 `probe_delayed_onset`（同一对象，位置不变，0–2 s 静音、2–4 s 发声、4–6 s 静音）的输出证实：源静音段对应的槽位输出严格零，发声段才被占用。因此两个样本的差异不是解码器行为不一致，而是音乐样本的槽位始终承载着低电平内容。

由此得到判据：**“是否严格为零”判定的是槽位在当前帧是否被占用，不能用于判定内容是否静音。** 反过来，任何按幅度阈值裁剪数据的做法都会连带删除待测的串扰与静音泄漏信号。

**曾经这里还记着一个「固定 15.0 dB 衰减」，已于 2026-08-18 撤回，理由见 9.6。** 一并撤回的还有那句「任何与参考解码器输出的 PCM 比较，必须先补偿时延与增益」——它把在一个解码器上标定的常量当成了对另一个解码器比较的前置条件，而同一段自己就写着「必须在每个新编码档位与解码器版本上重新标定，不得跨配置沿用」。

**时延保留，但同样不得直接用于与 DRP 的比较。** 4451 采样测自那条兼容性路径；保留是因为它有一部分能被独立佐证——见下文的容器侧拆解，2048 采样来自本仓库自己解析的 `elst`，不依赖任何解码器。剩余部分仍未复核。

4451 采样的构成已部分拆解。M1 的容器解析给出了其中的容器侧分量：

| 分量 | 采样数 | 来源 |
|---|---:|---|
| 容器 priming | 2 048 | `elst` 的 `media_time`，恰为一帧 |
| 编码器与解码器延迟合计 | 2 403 | 端到端 4 451 减去容器 priming |

同一码流的媒体时长比呈现时长多 4 864 采样，由前导 2 048 与尾部 2 816 组成。前导部分由 edit list 显式声明，尾部则只体现为媒体时长与编辑段的差值。

剩余的 2 403 采样仍未区分编码器与解码器各自的贡献，该拆分需要一个已知延迟的参考编码或解码路径，目前两者都不具备。这份拆解只解释早期兼容性路径上的历史观察；对该路径之外的任何比对，必须先在目标解码路径上重新标定整体对齐量，不能沿用 4 451。

### 9.5 编码链的时域扩散

`probe_delayed_onset` 的发声段边界在解码输出中被显著展宽：

| 边界 | 源位置 | 加流时延后的期望位置 | 实测非零位置 | 偏移 |
|---|---|---|---|---|
| 起始 | 96000 | 100451 | 96320 | −4131 |
| 结束 | 192000 | 196451 | 200638 | +4187 |

信号在期望位置前后各约 4100 采样处即已出现，前后基本对称，与两个 AC-4 帧（4096 采样）接近，符合 MDCT 重叠与对象重建时域处理的特征。扩散不会传得更远：距发声段两秒以上的区域仍严格为零。

该偏移量以 9.4 中的流时延为基准计算，因此**继承 9.4 的来源问题**：4451 采样测自早期兼容性解码路径，未经 DRP 复核。若该时延在 DRP 上重测后改变，或 M1 拆解 priming 后修正了它，扩散量必须同步重算。此处只记录**观察到的偏移**，不作为已确证的编码器特性。只有两侧扩散宽度之和不依赖所选的全局时延：本次观察为 `4131 + 4187 = 8318` 采样；它仍然只描述这条早期兼容性路径，不能外推到 DRP 或其他解码器。

对测试设计的约束：若沿用这份历史观察，**发声段之间的静音间隔必须大于 8318 采样；按 2048 采样的整帧取值时至少留五个 AC-4 帧**，否则相邻段会互相污染，静音泄漏与串扰测量到的将是该解码路径的时域扩散而非被测量本身。换用 DRP 或其他解码器时必须重新标定。案例 `probe_axes_single_object` 采用 24000 采样发声加 24000 采样静音，间隔满足当前观察下的要求。

## 10. Bootstrap 样本

当前已经验证过一条可作为首个结构样本的码流，特征为：

- AC-4 bitstream version 2。
- presentation version 1。
- 48 kHz、768 kbps。
- 每帧 2048 samples。
- Object Audio Main。
- A-JOC 20.1，9.1 object core。
- 单 presentation、单 group、单 substream。

该样本用于启动 MP4、`dac4` 和 TOC 解析。它不是完整 conformance vector，也不能替代程序化诊断母版。

## 11. 素材边界

- 自生成信号和元数据优先。
- 不把商业节目、客户媒体或来源不明的测试流提交到仓库。
- 授权测试流只允许通过本地路径或受控制品系统引用。
- 测试报告不得泄漏受限制码流的原始 payload。
